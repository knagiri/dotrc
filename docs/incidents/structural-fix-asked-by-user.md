# 「構造的に解決するか」をユーザーに問われるまで例外的な案を出していた

## 経緯

ユーザーは repo を問わず、agent が出した修正方針に対して「構造的に問題を解決するか？」と
問いかけることが多い。そう問われると、agent は大抵それまでの案より良い案を出す。つまり
良い案を出す能力はあり、その問いを自分で立てていなかった。

最初に出る案は、特定の問題に対して「この場合だけ例外的にこうする」という形が多い。例外の
分岐・特別扱いのフラグ・外部の状態を組み合わせた条件である。例外が要ること自体が設計の
ズレを示していることが多いが、問われるまでそこへ戻らなかった。

## 関連する別の型の例

ユーザーが「構造的に解決するか」と問うた場面ではないが、外部の状態を組み合わせた例外的な
条件が、条件の想定しない経路で誤りうる型の例がある。レビューループの判定役が修正指示で、
外部ライブラリ（BullMQ）のワーカーの状態を組み合わせた停止判定の条件を指定し、修正役が
そのとおり実装した。後の review の指摘によれば、この条件は pause（公開 API）という、条件が
想定していなかった経路で誤る。この指摘は未再現で、確認した版も記録されていない。参照先の
`docs/incidents/review-loop-own-fix-unverified.md` の主因は、修正指示を一次情報で検証しな
かったことである。「ライブラリの想定するライフサイクルに乗らない形だった」という見立ては
この doc の解釈で、参照先には無い。

## 観測

ユーザーとのやり取りの中での観測で、特定の transcript・コマンド出力は残っていない。問いの
後に出た案が良くなったという評価はユーザーによるもので、件数を数えたものではない。

## 直し方

修正方針を決めるとき、特に例外・回避策・外部の状態を組み合わせた判定を足すときに、
agent が自分で「構造的に解決するか」を問う rule を常時ロードで置いた。範囲が大きく広がる
ときは黙って作り直さず、2 案と広がる範囲を示して人間の判断に回す。レビューの判定役も同じ
観点で diff を見る。
