# 重い CLI を xargs -P 32 で件数分起動し、共有マシンの load が 40 を超えた

## 経緯

複数の Claude session が同時に動く 16 コアの共有マシンで、ある session が scratchpad に書いた
scan スクリプトを流した。スクリプトは対象の一覧を `xargs -P 32` に渡し、Python 製 CLI
（aws CLI）を 1 件ごとに起動していた。

load average が 40 を超え、他の session の応答や tmux / fzf の操作が目に見えて重くなった。
API 呼び出し自体は軽く、CPU はインタプリタの起動と import に費やされていたと推定している
（未計測。プロファイルは取っていない）。

誤りは 2 つの掛け合わせにある。

- 件数分のプロセスを重いランタイムで起動する形を選んだ（1 件あたりのコストの大半が起動）
- 並列度をコア数（16）の 2 倍に置いた（共有マシンであることを勘定していない）

## 観測

スクリプトの形（一般化したもの）:

```
<一覧を出すコマンド> | xargs -P 32 -n 1 aws <service> <operation> ...
```

観測は報告ベースで、この doc の作成時に再現はしていない。

- `nproc` は 16
- 実行中の load average は 40 超
- 同時に動いていた対話 session と tmux / fzf の操作が体感で重くなった

## 直し方

- 並列度の既定を `nproc` の半分以下にし、超えるなら理由を明示する
- バッチ API や 1 プロセス内での並列化（SDK + thread pool）を先に検討し、重い CLI を件数分
  起動する形は最後の手段にする
- 長時間のバッチは `nice -n 10` で起動する
- 全件を流す前に少数件で所要時間と load を見る

scan のような処理そのものは禁止しない。
