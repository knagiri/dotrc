# review loop が自分で出した修正指示の誤りを検証しないまま収束した

## 経緯

外部 bot の review が付かない PR で、`pr-review-loop` の判定役・修正役だけで review が回った。

- 1 巡目の判定役が `findings_to_fix` で分岐条件を具体的に指示した。外部ライブラリ BullMQ の
  ワーカーの `error` イベントについて、「`isRunning()` が false かつ closing でないとき」は
  worker の停止として error で出す、という条件である。修正役はそのとおりに実装した
- 2 巡目の判定役は前巡の commit に欠陥なしとした
- 3 巡目の判定役は `findings_to_fix: []` を返し、loop は収束した

その後の別の review で、この条件が誤りと判明した。指摘によれば、BullMQ は `pause()` で main loop を
抜けたあと `run()` の finally で running を false にするため、pause 中の一時的なエラーも停止扱いに
なる。同じ review は、公開 API があるのに不要な型キャストをしている点も挙げた。

## 何を誤ったか

上の経緯は、各巡の verdict の結果と後の review の指摘として観測できた事実である。以下は
観測ではなく、loop の構造から導いた推測で、いずれも未確認である。

- 3 巡目の判定役が直前の小修正だけを見て収束を返した可能性がある。判定 prompt は毎巡
  `gh pr diff`（PR 全体）を読むよう指示していたので、実際に何を読んだかは分からない
- loop 自身が出した修正指示の条件を、誰も一次情報で検証し直していない。判定役に渡るのは却下済み
  gate の `<GATED_CARRYOVER>` だけで、前巡までに loop が出した `findings_to_fix` は渡されて
  いなかった（prompt の構造から確認できる事実）。後続の判定役が、その条件が loop 自身の指示
  だったことを知らずに実装を読んでいた可能性がある
- 外部ライブラリの実ソース・型定義に当たる巡が無い。専門 agent は 1 巡目だけ走り、3 巡目以降は
  correctness / 安全性に絞るが、ライブラリの挙動の前提を確かめる指示はどの巡にも無かった
  （これも prompt の構造から確認できる事実）

これらが重なると、loop が持ち込んだ不具合が残ったまま merge へ進みうる。

## 観測

transcript が残っておらず、実行したコマンドと出力は無い。再現もしていない。BullMQ の
`pause()` / `run()` の挙動は後の review の指摘に基づくもので、確認した版は記録されていない。

## 直し方

収束と判定する前段に監査巡を置いた。前回の監査以降に修正役がコードを変えていれば、手順 3 へ
進む前に監査モードの判定役を 1 回 dispatch する。監査役には過去の全巡の `findings_to_fix` を
`<PRIOR_FIXES>` として渡し、PR の base からの差分全体を対象に、条件・API の挙動の前提を
指定した指示を一次情報（lock file で固定された版の実ソース・型定義、repo 内なら実装）と照らして
検証し直させる。監査の verdict が収束条件（直すもの無し・実行する処置無し・blocker 無し・
mergeable）を満たせば上限を消費せず収束へ、満たさなければ通常の 1 イテレーションとして数える。
