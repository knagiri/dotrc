# proofread-doc

doc の校正を 4 パスに分けて順に回す。パスごとに検出対象も直しかたも別物なので、まとめて
1 回で見ずに分ける。特に文体パス（パス 3）で止めると「書きすぎ」が残る。

**判定基準はこの skill には書かない。** 実体は `doc-authoring` rule 側にあり、ここは進め方
だけを持つ（二重管理を避けるため）。

## 手順 0: 基準を読む

`doc-authoring` rule は `paths`（`**/*.md` / `**/*.mdx`）でスコープされており、対象 doc を
Read / Edit した時点で自動的にコンテキストへロードされる。**既にロード済みならそれを使い、
無いときだけ Read する。** 未ロードで Read するパスは、dotrc の checkout 内で作業している
なら `dot/claude/rules/doc-authoring.md`、それ以外は `~/.claude/rules/doc-authoring.md`。
以下の各パスは、この rule の同番号の観点を指す。

対象 doc を通読し、doc の種類（designdoc / ADR / spec / README …）と読者を把握する。パス 2 と
パス 4 の判断は読者が誰かに依存する。

## パス 1: 作成過程の痕跡

**検出**: 出典・検証の注記、初案と撤回のナラティブ、先回りの弁明、訂正のメタ文（rule 観点 1）。

doc 全体を頭から読んで拾う。grep で機械的に当てられるのは一部だけ（「当初」「なお」「ではなく」
「確定している」等）なので、当たりを付ける用途に留め、検出そのものは通読で行う。

**直しかた**: 注記は中立な事実文へ書き換える。初案は削るか代替案セクションへ移す。弁明は
削る（理由が要るなら 1 箇所だけ残す）。訂正のメタ文はここで消さず、パス 2 へ送る。

最初にやるのは、ここで消える量が最も多く、後続パスの対象を減らせるため。

## パス 2: 叙述の因果順

**検出**: パス 1 で送られた訂正のメタ文を起点にする。メタ文が要る箇所は、たいてい語順が
因果と逆になっている（rule 観点 2）。

**直しかた**: 「背景 → 選択 → 帰結」に並べ替え、メタ文自体を削除する。

**このパス特有の注意**: 常に適用しない。概要・要約など読者がまず結論を求める箇所では結論
先出しが正しいので、並べ替えない。判断がつかなければ並べ替えずに残し、後述の「確認に回す」
へ送る。

## パス 3: 文体

**検出**: 太字・スローガンの濫用、テンプレ断片、重複、生英語混じりの造語（rule 観点 3）。

repo に機械 lint（textlint 等）があれば先に実行し、拾えるものは任せる。

```
ls .textlintrc* 2>/dev/null; rg -l 'textlint|prh' package.json 2>/dev/null
```

lint があれば実行して指摘を消化し、**残りの層を自分で見る**。lint は太字の多寡・テンプレ
断片・セクション間の重複を拾わない。lint が無ければ全部を自分で見る。

**直しかた**: 太字を落とす、テンプレを散文に織り込む、重複は 1 箇所に寄せて他は参照にする、
造語は訳すか原語に戻す。

## パス 4: 内容の取捨選択

**パス 3 で終わらせない。** 文体を全部直しても、doc が実装台帳になっている限り分量は減らない。
このパスが本体である。

**検出**: 各記述を rule 観点 4 の 4 基準（外部との契約 / コードに書けない why / 他チームへ課す
要件 / 計測・評価の枠組み）に照らし、どれにも該当しないものを削除候補にする。セクション単位
ではなく記述単位で当てる。付随ルールの「不採用の宣言でも設計情報を持つものは残す」もここで
判定する。

**直しかた**: 削除候補を落とす。コードや実装 PR から読める what は、必要なら参照リンクに
置き換える。

**このパス特有の運用**（rule 観点 4 の付随ルール 2・3 に対応）:

- **レビュー済みの判断は削る前に確認する。** 対象 doc の git 履歴・PR コメントを見て、その
  記述が過去のレビューで「残す」と合意されていないか確かめる。合意があれば独断で削らず、
  確認に回す。

  ```
  git log --oneline -- <doc path>
  gh-pr-comments <PR>   # doc を追加・変更した PR がわかる場合
  ```

- **削除は可視化する。** 落とした内容とその出典（git 履歴の commit、実装 PR の番号）を PR 本文
  に列挙し、情報が消えていないことを示す。削減量だけを報告しない。

## 結果の提示

自分で直すものと確認に回すものを分ける。

**自分で直す**: パス 1・パス 3 の全部と、パス 4 のうち 4 基準のどれにも明らかに該当しない
記述。判断が機械的で、間違っても git 履歴から戻せる範囲。

**確認に回す**: パス 2 の並べ替え可否が微妙な箇所、レビュー済み判断の削除、4 基準への該当が
グレーな記述、doc の構成そのものを変える提案。いずれも著者の意図か過去の合意に依存し、
doc 本文だけからは判断しきれない。

報告は「パスごとに何を何箇所直したか」と「確認に回した項目」を分けて出す。差分が大きい場合は
パスごとに commit を分けると、レビュー側がパスの粒度で追える。
