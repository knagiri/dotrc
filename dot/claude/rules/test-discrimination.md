## テストの判別力を確かめるときの細則（変異・fixture・後始末）

`evidence-over-guesswork.md` §4（足したテストがガードである証拠を示す）を実行するときの細則。
テストを書く・直す場面でしか要らないので、テストファイルを触ったときだけロードされるよう
`paths` でスコープする。

### 1. 変異を撃つ前に、破壊的な到達先が塞がれていることを確かめる

変異させるコードパスが実環境の状態に触れうる（ファイル削除・外部 API 呼び出し・プロセス停止・
ネットワーク書き込み）なら、変異したテストはその操作を本当に実行しうる。「対処コマンドを
提示する」を「実行する」へ変える変異がこの形で、規約どおりの手順がそのまま事故の引き金になる。
撃つ前に、到達先が stub で塞がれていることを対照で確かめる。stub を置いた事実では足りず、
テスト対象の実行経路で呼び出しが stub に捕まることを 1 本の subtest で示す（PATH 等の差し替えが
対象の経路に効いているとは限らないため）。stub は実コマンドへ forward しない。
`exec /bin/rm "$@"` のような素通しは呼び出しを記録しても塞いではおらず、stub ではない。

これは `evidence-over-guesswork.md` §5 の対照原理と同根で、判別力の確認が「ガード対象が無いと
落ちる」を確かめるのに対し、こちらは「破壊的な到達先が塞がれている」を確かめる。

### 2. 変異を当てても落ちないなら、テストより先に変異を疑う

落ちない原因は、テストに判別力が無いことのほかに、変異そのものが効いていないこと（未適用・
no-op・到達不能・二重ガード）がある。後者をテストの欠陥と誤診すると、健全なテストを壊しに行く。
fixture やアサーションを触る前に、変異側を次の順で確かめる。

- `diff` 等で変異が実際に適用されたことを観測する。sed の pattern 不一致はエラーにならず
  黙って何もしないので、適用の成否は見ないと分からない
- 適用済みで落ちないなら、その変異が単体で挙動を変えるかを確かめる（別の入力を通す・
  該当コードを直接呼ぶ等で観測差が出るか）。変えないなら「その分岐は単体では挙動に
  効かない」というコードについての所見（no-op・到達不能）であり、テストの欠陥とは
  別物。変えるなら、そこで初めてテストの判別力を疑う
- 2 箇所を同時に壊して初めて差が出るなら二重ガードである。「1 つずつ壊す」変異では原理的に
  差が出ないので、組み合わせて壊す

### 3. 壊れうる入力形が fixture に入っているかまで見る

「ガード対象が無いと落ちる」だけでは足りない。実装を無効化して落ちることは fixture が正常形
しか持たなくても成立するので、判別力チェックだけでは入力側の穴が残るため。対象は全テストでは
なく、既存データの末尾形状・空・有無に依存して黙って壊れる処理（ファイルへの追記、文字列連結、
parse）に絞る — 追記なら「末尾改行あり / なし / 空ファイル / 既存 entry なし」が最小の組になる。

### 4. 「合成データを commit するな」型の指示との両立

検証に使ったスクラッチ artifact（一時データファイル・使い捨てスクリプト）を commit しない
ことと、回帰テストを書かないことは別物で、両立する。fixture をテスト内で生成すれば、データ
ファイルもスクリプトも repo には残らない。指示が回帰テストそのものを禁じていると読めるときに
限り、確認して止まる。

### 5. 変異は退避したコピーから戻す

変異を当てる前に対象ファイルのコピーを退避し、戻すときはそのコピーから戻す。
`git checkout -- <path>` / `git restore` は index の内容に戻すので、stage していない（変異前の）
未 commit の変更まで一緒に消える。テストと実装を書きかけのまま判別力を確かめるのが普通の順序
なので、この形は例外ではない。戻したあと `git diff` で変異前と同じ差分に戻っていることを
確かめる。

実例: dotrc/docs/incidents/mutation-revert-via-git-checkout.md
