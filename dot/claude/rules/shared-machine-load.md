## 共有マシンで重いバッチを流すときの負荷の抑え方

このマシンは複数の Claude session と、人間の端末操作（tmux / fzf 等）が同時に使っている。
大量件数を処理するスクリプト（scan・一括取得・一括変換など）を書く・流すときは、1 session が
CPU を使い切らない形にする。処理そのものは禁止しない。避けるのは重すぎる処理の形である。

バッチ処理は領域を問わずどの repo の session でも起こるので、`paths` を付けず常時ロードする。

典型的な失敗は「件数分のプロセスを重いランタイムで起動する」形と「コア数を超える並列度」の
掛け合わせである。たとえばコア数の 2 倍の並列度で重い CLI を 1 件ごとに起動すると、他の
session や端末操作まで目に見えて重くなりうる。

実例: dotrc/docs/incidents/heavy-cli-xargs-overload.md

### 1. 並列度の既定は nproc の半分以下

`xargs -P` やワーカー数の既定は `nproc` の半分以下にする。超えるなら、理由（I/O 待ちが
支配的で CPU をほぼ使わない等）をスクリプトか報告に明示する。

1 session がコアを使い切ると、対話中の session や端末操作まで巻き込むため。

### 2. 1 件 1 プロセスは最後の手段

件数が多いときは、次の順で検討する。

1. バッチ API（まとめて取得できる list 系・bulk 系のエンドポイント）
2. 1 プロセス内での並列化（SDK + thread pool / async 等）
3. 重いランタイム（Python / Node 製 CLI）を件数分起動する形

3 は最後の手段にする。1 件あたりの処理が軽いほど、コストの大半が起動になりやすく、並列度を上げるほど無駄が増えるため。

### 3. 長時間のバッチは `nice -n 10` で起動する

数分以上かかりそうなバッチは `nice -n 10 <cmd>` で起動する。CPU が競合したときに対話側を
優先させるため。`nice` は Claude Code が照合前に剥がす process wrapper なので、permission の
照合には影響しない（[bash-command-constraints.md](./bash-command-constraints.md) 参照）。

### 4. 全件を流す前に少数件で見積もる

件数 × 1 件あたりのコストが大きそうなら、まず少数件（10〜100 件程度）で試し、所要時間と負荷
（`uptime` の load average 等）を見てから全件を流す。少数件の結果から全件の時間と load を
外挿し、マシンを長く占有しそうなら §1〜§3 の形を見直す。

全件を流してから重さに気づくと、その間ずっと他の session を巻き込み続けるため。
