## repo の doc の役割分担

repo の doc（README / CLAUDE.md / 設計 doc / 経緯の記録）に何を書き、何を書かないかの指針。
置き場所ではなく役割を規定する。既存 repo では置き場所の慣習に従い、役割の分担だけをそろえる。
doc を書く場面は repo を問わず起こるので、`paths` を付けず常時ロードする。

役割が混ざると、読者は目的の情報を探すために無関係な記述を読み続けることになり、同じ内容が
複数の doc に散って片方だけ更新される。典型は README に詳細な意思決定・前提・経緯が流れ込む形で、
入口が入口として機能しなくなる。

実例: dotrc/docs/incidents/main-commit-without-pr-flow.md

### README

開発者向けの入口。目的、doc への index、開発準備の手順のような一般的な内容を書く。

詳細な意思決定・前提・経緯は一般に書かず、それぞれの役割の doc へ回して index から辿れるように
する。README は最初に読まれる doc なので、詳細を抱えるほど入口としての見通しが悪くなり、しかも
詳細の正典が README と設計 doc の 2 箇所に割れて食い違うため。

### CLAUDE.md

その repo における AI agent の方針とガイドライン。特に、ユーザーと agent の権限の境界を書く。

- agent が自律でやってよいこと
- 人間の承認が要ること
- 人間しかやらないこと

境界が書かれていないと、agent は repo ごとの事情を知る手段が無く、global な既定で判断する。
その既定が repo の運用と合わないとき（承認を挟むべき操作を自律で進める等）、誤りは実行後に
しか見えない。

global な rule の複写や開発準備の手順（README の役割）は書かない。複写は global 側の改訂に
取り残され、手順は README と二重になるため。

### 設計 doc

設計判断とその理由、前提を書く。現時点で正しい状態を記述し、そこへ至った経緯の物語にしない。

読者が知りたいのは今どうなっているか・なぜそうなっているかであり、過程の記述は読解の負荷に
しかならないため。経緯が判断の根拠として要るなら、経緯の doc へポインタで参照する。

### 経緯・incident

何が起き、どう判断したかを書く。設計 doc や規約からはポインタで参照される側に置く。

経緯は書いた時点で確定して変わらない記録なので、現時点の状態を書く設計 doc と分けておけば、
設計 doc を更新しても経緯が失われず、経緯を足しても設計 doc が膨らまない。

### baseline の欠けた repo

remote・PR フロー・CI が欠けた repo で作業していると気づいたら、`repo-baseline` skill の適用を
提案する。適用はユーザーの承認後に行う。

欠けたままだと、PR を前提とする `worktree-scope.md` §5 の委譲も、CI の結果を見て merge する判断も
成り立たない。agent はそれを前提が無いとは認識せず、main への直接 commit で作業を進めてしまう。
