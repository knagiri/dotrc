## 人が読むドキュメントの執筆・校正の観点

designdoc / ADR / spec / README など、人が読む文書を書く・直すときの観点集。Markdown を
触ったときにロードされれば足りる文脈依存の規約なので `paths` でスコープし、常時ロードは
しない。

観点は 4 つあり、それぞれ検出のしかたも直しかたも別物である。特に、**文体（観点 3）だけ
直しても「書きすぎ」は残る**。消すには内容の取捨選択（観点 4）まで踏み込む必要がある。
以下はいずれもハード禁止ではなく理由付きの指針で、理由が当てはまらない文脈では従わなくて
よい。

校正を手順として回すときは `proofread-doc` skill を使う。判定基準はこの rule が持ち、
skill は進め方だけを持つ。

### 観点 1: 作成過程の痕跡を消す

doc は「最終形の記述」であって「そこへたどり着くまでの記録」ではない。過程が残った箇所を
消す。AI に書かせた doc で最も頻出し、修正効果も最も大きい。

- **出典・検証の注記**: 「〜で確定している（user）」のようなセッション内の情報源注記や、
  「実 repo に該当処理なし」のような調査行為が透けた表現。中立な事実文に直す
- **初案と撤回のナラティブ**: 「当初は A 案を検討したが B に決めた」「当初 nullable で
  設計したが実装では必須にした」。確定した設計を現在形で書き、迷った案は代替案セクションへ
  移す
- **先回りの弁明**: doc 内で誰も提起していない反論への防戦（命名判断の正当化を複数箇所で
  繰り返す等）。レビュー指摘に答えた痕跡であることが多い。削除する。理由が要るなら 1 回だけ
  書く
- **訂正のメタ文**: 「X は前提条件ではなく結果である」のような、過去の誤読を打ち消す構えの
  文。文を足して直すのではなく、観点 2 で解消する

読者はその doc がどう作られたかを知らないので、過程の記述は情報にならず、読解の負荷だけが
残るため。

### 観点 2: 叙述の因果順を整える（ケースバイケース）

「背景 → 選択 → 帰結」の順で書けば、読者は誤った因果を組み立てようがなく、訂正のメタ文
自体が要らなくなる。

例: 「撮り直しができないから使い回す」は制約駆動の設計に読める。これを「判定に使った
フレームを使うほうが確実 → だから使い回す → その帰結として撮り直し装置を置かない」と
並べ替えると、「〜は前提ではなく結果」という宣言文が丸ごと消せる。

ただし常に適用する規則ではない。概要・要約・レビューコメントなど、読者がまず結論を求める
文脈では結論先出しが正しい。違反シグナルは語順そのものではなく、**訂正・弁明のメタ文を
足さないと誤読される構成になっている**こと。メタ文が要ると感じたら、メタ文を書くのではなく
語順を疑う。

### 観点 3: 文体

repo に機械 lint（textlint 等）があれば拾える層はそちらに任せる。以下は lint が拾えず、
人 / AI のレビューが担う層。

- **太字とスローガンの抑制**: 「設計の核」「最重要」「恒久」のような抽象概念への命名・掲揚を
  やめる。太字は 1 doc に数回まで。強調が増えるほど 1 つあたりの強調は効かなくなる
- **テンプレ断片の禁止**: 「メリット= / デメリット= / 不採用理由=」「根拠:」+ 箇条書きの
  ような機械的テンプレをやめ、散文に織り込む。埋めるべき枠があると、書くことが無い項目まで
  埋めてしまうため
- **重複の一本化**: 同じ設計判断・不変条件を複数セクションで繰り返さない。1 箇所で述べ、
  他は参照にする。重複は分量を増やすうえ、片方だけ更新されて食い違う
- **生英語混じりの造語をしない**: 例:「最小 blast radius な組み込み」。定訳のある語は訳し、
  無い技術用語は原語のまま置く

### 観点 4: 内容の取捨選択（実装台帳の解体）

文体を全部直しても残る「書きすぎ」の正体は、doc が「決めたこと・実装したことの網羅台帳」に
なっていることである。各記述を次の 4 基準で判定し、どれにも該当しなければ削る。

1. **外部との契約** — 別リポジトリ・別システムへ要求する API 契約と、その保証の理由
2. **コードに書けない why** — なぜ optional にしたか、なぜ transaction に入れないか等の根拠
3. **他チーム・別ワークストリームへ課す要件**
4. **計測・評価の枠組み** — モニタリング項目、成功基準、サイジングの根拠

削る対象の典型は「コードや実装 PR から読める what」である。GraphQL 入力規則の詳細、payload の
受け渡し形、分岐の列挙、実装スケッチの大半がこれに当たる。コードが一次情報である以上、doc に
写した what は更新されずに腐り、読者は結局コードを読むため。

付随ルールが 3 つある。

- **「不採用の宣言」でも設計情報を持つものは残す。** 例:「専用の enable フラグは設けず設定値の
  有無で兼ねる」は不採用の記述に見えて、設定設計そのものを述べている
- **レビュー済みの判断を黙って覆さない。** 過去のレビューで「残す」と合意された記述を削る
  ときは確認を挟む。合意の経緯は doc 本文からは読めないため
- **削除は可視化する。** 落とした内容の出典（git 履歴・実装 PR）を PR 本文に明記し、情報が
  失われないことを示す。可視化がないと、削減は「情報を消した」としか見えない

### 適用場面

- **執筆時**: AI に doc を書かせるとき・自分で書くときの抑制として
- **校正時**: 既存 doc の校正依頼を受けたとき。4 パスを順に適用する。文体パスと内容パスは
  別物なので、両方やる
- **レビュー時**: 他人の doc PR をレビューするときの観点として

---

由来: 業務 repo で AI に生成させた designdoc を人手で校正した経験（2026-08）から。文体を
一通り直しても「書きすぎ」は残り、記述ごとに残す理由を問う内容の取捨選択（観点 4）まで
踏み込んで初めて解消した。観点 1〜2 は、その校正で最も頻出した「過程の記録が最終形に
混ざる」型の指摘を切り出したもの。
