## 推測で進めない — 一次情報・再現・立ち止まり・テスト・空振りでない確認で裏取りする

共通原理は『裏が取れるまで推測で先へ進めない』。裏取り無しの設計・修正は、外すと後戻りが
大きく、外したことに気づかないまま積み重なるため。作業の進め方そのものなので `paths` を
付けず常時ロードする。効くのは (1) 設計・実装の着手時、(2) ローカル再現が難しいエラーの対応時、
(3) 同一機能の 3 回目の修正前、(4) テストを足して PR を出す前・決定論的な不具合を直したとき、
(5) 測定で効果を主張するとき（渡された実測を読むときを含む）と、不在・失敗しなかったことを
成功条件にするとき。

### 1. 公式ドキュメントを確認する前に計画・実装を開始しない

新しいライブラリ・API・ツールを使う前に公式ドキュメント・サンプルを確認しきり、推奨設定が
あればそこから始める。記憶や類推で組んだ設計は実際の契約とずれ、後で設計ごとやり直しになる
ため。確度の高い一次情報が手元にあればこの限りではない。

**間違えると黙って壊れるクラスは、外部ツールでも書く前に裏を取る**。即エラーになる誤りは
実行すれば分かるので対象外で、エラー無しに別解釈で通るものだけがテストも gate もすり抜ける。

- 予約文字・エスケープ・quoting・format 展開 — 例: tmux の window 名は format 展開され `#S` が化ける
- 解決順（同名設定が複数経路にあるときどれが勝つか） — 例: ssh の `-o` は先勝ちで、後ろに足しても効かない
- config 既定に依存して黙って付く副作用 — 例: `git worktree add -b` に `origin/HEAD` を渡すと upstream が `origin/main` になる

man を読むだけで終えず、実効値を出せるツールで確かめる（`ssh -G <host>`、
`git config --list --show-origin`、`git rev-parse --abbrev-ref <branch>@{upstream}` 等）。
読んだ内容と実効値の食い違いこそがこのクラスの典型で、手元の config や引数との組み合わせで
初めて決まるため。

実例: dotrc/docs/incidents/upstream-autosetupmerge-origin-main.md

### 2. ローカルで再現できないエラーを推測で修正しない

CI/CD やリモート環境のエラーは、ログとエラーメッセージを読み切って原因の仮説を 1 本に絞って
から直す。確認に 1 サイクルかかる環境で推測を撃つと、外れるたびにそのコストを払い根本原因に
迫らないため。手元で即座に試せるものは試してよい。

### 3. 同じ機能の修正が 2 回失敗したら立ち止まる

同じ不具合への fix が 2 回続けて効かなければ、3 回目の前に立ち止まりアプローチを見直す。
連続して外れるのは前提の理解が誤っているサインで、同じ前提で撃っても外し方が変わるだけのため。
見直しを判断力の落ちた自分でやると同じ轍を踏みやすいので、まず `second-opinion` skill で
fresh な視点を挟む。

### 4. 足したテストがガードである証拠を示す — 決定論的な不具合には再現テストを同じ PR に入れる

100% 再現するバグを直したら、再現条件を突くテストを同じ PR に含める。既存 suite があることは
ガードの根拠にならない。付けずに直すと同じ回帰が黙って戻り、「テストは通っている」ので
気づけないため。

**判別力を確認する**: 足したテストがガード対象の無い状態で実際に落ちることを確かめ、落ちる
まで詰める（feature 実装のテストも同じ）。ガードの実体は、テストがあることではなく対象の有無で
結果が変わる差分にあるため。

- **既存シンボルの挙動を変える修正** — 修正前のコード（`git show <base>:<path>` 等）に掛けて落ちることを確かめる
- **新しいシンボルを導入する変更** — 修正前コードではシンボル不在で落ちるだけで判別にならないので、新しいコード側を 1 箇所ずつ変異させて捕まえることを確かめる（TDD の red でも埋まらない）

**例外**: 再現条件をテストに落とせない場合（外部環境・実 API・タイミング依存など）は、理由を
PR 本文に書く。落とせるのに書かなかったケースを例外に紛れ込ませないため。

変異の安全な撃ち方・落ちないときの切り分け・fixture の入力形・後始末の細則は
`test-discrimination.md`（テストファイルを触るとロードされる）にある。

### 5. 確認が空振りしていないか確かめる — 対照を取り、不在を待つ前に対象の存在を確かめる

「X を入れたら Y になった」を主張する測定は X が無い状態も測り、交絡が無いかまで見る。X 無しでも
Y なら X の効果は何も示されていない。§4 の判別力と同じ形で、裏取りの実体は介入の有無による
差分にある。他者へ渡す測定には対照を含める（渡した先で誤りが展開するため）。渡された実測は
再計測しなくてよいが、対照が手順に無ければ結論を保留する。

**不在を成功条件にする確認は、この空振りが常に付きまとう特殊ケース**である。「無いこと」
「消えたこと」「失敗しなかったこと」は対象がまだ出現していない時点でも真になるので、
**存在・出現を確認してから待機に入る**。確認できない待機は根拠にしない。非同期に登録される
リソース（background session、CI run、デプロイ等）は起動コマンドの return 時点では一覧に
載っていないことがあり、特に踏みやすい。観測結果を doc や設計の前提に記録するときは特に
効かせる。誤りが派生した記述すべてに及ぶため。

実例: dotrc/docs/incidents/absence-wait-before-registration.md
