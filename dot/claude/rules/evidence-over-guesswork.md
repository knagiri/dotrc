## 推測で進めない — 一次情報・再現・立ち止まり・テスト・空振りでない確認で裏取りする

不完全な理解のまま推測で動くのを戒めるルール。共通原理は『裏が取れるまで推測で先へ進めない』。
一次情報を確認しきる・エラーを根本原因まで特定する・失敗が続いたら立ち止まる・足したテストが
ガードである証拠を示す・確認そのものが空振りで真になっていないか確かめる、の 5 つで裏取りを
担保する。裏取り無しに書いた設計・修正は、当たれば速いが外すと後戻りが大きく、外したことに
気づかないまま積み重なると被害が拡大するため。

このルールは領域固有ではなく作業の進め方そのものなので `paths` を付けず常時ロードする。
発火する状況は下の 5 セクションに対応し、それぞれ (1) 設計・実装の着手時、(2) CI/CD・
リモートなどローカル再現が難しいエラーの対応時、(3) 同一機能の 3 回目の修正着手前、
(4) テストを足して PR を出す前、および決定論的に再現する不具合を直したとき、(5) 測定で何かの
効果を主張しようとしたとき（他者から渡された実測を読むときを含む）、および不在・消滅・
失敗しなかったことを成功条件に書こうとしたとき、で効く。

由来: dotrc#10

### 1. 公式ドキュメントを確認する前に計画・実装を開始しない

新しいライブラリ・API・ツールを使う設計や実装に着手する前に、公式ドキュメント・公式サンプルの
確認を完了させる。推奨設定（recommended defaults / quickstart）があればそれを出発点にする。

一次情報を確認しきる前に組んだ設計は、記憶や類推に基づく推測を含みやすく、API の実際の
契約や前提とずれる。ずれた土台の上に実装を積むと、後で一次情報に当たった時点で設計ごと
やり直しになり、確認を先にやるより高くつくため。既に確度の高い一次情報を持っている（最近
読んだ・手元にサンプルがある）場合はこの限りではない。

**間違えると黙って壊れるクラスは、外部ツールでも書く前に裏を取る**。外部ツールの挙動全般まで
広げると毎回 man を引くことになりコストが釣り合わないので、エラーにならず別の解釈で通って
しまうものに絞る。存在しない flag のように即エラーで返る誤りは実行すれば分かるので対象外で、
黙って別解釈されるものだけがテストも gate もすり抜けて後から発覚する。このクラスに当たるのは
次のものである。

- 予約文字・エスケープ・quoting 規則・format 展開 — 例: tmux の window 名は format 展開
  されるので、`#S` や閉じない `#{` を含む名前がエラー無しに別の文字列へ化け、名前一致に
  頼る dedupe が破れる
- 解決順（同名の設定が複数経路にあるとき、どれが勝つか） — 例: ssh のオプションは
  first obtained value wins なので、既存の `-o BatchMode=no` の後ろに `-o BatchMode=yes` を
  足しても効かない。後勝ちを前提にすると正しく見える
- config 既定に依存して黙って付く副作用 — 例: `git worktree add -b <branch> <path> origin/HEAD`
  のように remote-tracking ref を start point に渡すと、`branch.autoSetupMerge` の既定で
  新規ブランチの upstream が `origin/main` になり、`git status` の ahead/behind や
  `@{upstream}` を使う判定（例: `git log @{upstream}..HEAD` が空に見える）が
  `origin/main` 基準に狂う（素の `git push` は push.default=simple の既定なら upstream 名と
  ブランチ名の不一致をエラーで止めるので、このクラスには当たらない）

man を読むだけで終えず、実効値を出せるツールがあればそれで確かめる（`ssh -G <host>`、
`git config --list --show-origin`、作った直後の `git rev-parse --abbrev-ref <branch>@{upstream}`
等）。読んだ内容と実効値が食い違うことこそがこのクラスの典型で、解決順も既定値も、手元の
config や呼び出し側の引数との組み合わせで初めて決まるため。

由来: dotrc#75 / dotrc#124

### 2. ローカルで再現できないエラーを推測で修正しない

CI/CD やリモート実行環境など、ローカルで再現しにくいエラーは、ログとエラーメッセージから
根本原因を特定してから直す。部分情報からの推測で場当たり修正を繰り返さない。

再現しにくい環境では、修正が効いたかの確認に 1 サイクル（push → CI 待ち等）かかる。推測で
撃つと外れるたびにそのコストを払い、根本原因に迫らないまま試行回数だけ増えるため。まず
ログ・エラーメッセージを読み切り、原因の仮説を 1 本に絞ってから直す。ローカルで即座に試せる
ものは試してよい（このルールは再現が難しい環境のエラーに適用する。手元で 1 秒で回せる
ものまで縛る意図はない）。

### 3. 同じ機能の修正が 2 回失敗したら立ち止まる

同じ機能・同じ不具合に対する fix コミットが 2 回続けて効かなかったら、3 回目の修正に進む前に
立ち止まる。公式ドキュメント・関連イシュー・ログを再確認し、アプローチ自体を見直す。

fix が連続して外れるのは、個々の修正のミスではなく前提の理解が誤っているサインであることが
多い。同じ前提のまま 3 回目を撃っても外し方が変わるだけで、前提を検証し直すほうが近道に
なるため。「あと一手で直る」感覚は、外れた 2 回がまさに否定している。

立ち止まったあとの「再確認・見直し」を、判断力が落ちた親が自力でやると同じ轍を
踏みやすい。そこで `second-opinion` skill が具体的手順を定めている。fresh context の
最賢モデル sub-agent に、一次情報の読み直しを含む根本原因の診断とセッション劣化の
診断を仰ぎ、「継続」か「仕切り直し」かを判定する。上の再確認を自力で始める前に、
まずこの skill で fresh な視点を挟む。

### 4. 足したテストがガードである証拠を示す — 決定論的な不具合には再現テストを同じ PR に入れる

100% 再現するバグを直したら、その再現条件を突くテストを修正と同じ PR に含める。既存 suite が
あることは、それがそのバグをガードしている根拠にならない。

既存テストが修正前のコードでも pass するなら、そのテストは当該バグを何もガードしていない。
そして決定論的に 100% 再現するなら、その再現条件は多くの場合テストに落とせる（落とせない
場合は後述の例外）。だからガードを付けない理由は弱い。付けずに直すと、同じ回帰が次の変更で
黙って戻り、しかも「テストは通っている」ので気づけない。

**判別力を確認する**: 追加したテストが、ガード対象が無い状態では実際に落ちることを確かめる。
落ちないなら、そのテストは対象を捕まえていない（fixture が小さすぎる・再現条件を満たして
いない等）ので、落ちるまで詰める（変異で確かめている場合は、テストを触る前に後述の
「変異を当てても落ちないなら」の確認を通す）。テストを足したという事実ではなく、ガード
対象の有無で結果が変わるという差分が、ガードの実体だから。

この確認はバグ修正に限らず、feature 実装で足したテストにも要る。テストの名前がガードを
主張していても、fixture が条件を満たしていなければガード対象を消しても落ちない。名前と実体の
乖離は読み手には見えないので、テストがあること自体が誤った安心になる。

示し方は変更の形で 2 つに分かれる。

- **既存シンボルの挙動を変える修正** — 修正前のコード（`git show <base>:<path>` 等で取り出す）に
  掛けて落ちることを確かめる
- **新しいシンボル（新 package・新関数）を導入する変更** — 修正前コードにはテストが参照する
  シンボルが無いので、当ててもシンボル不在それ自体で落ちるだけ（compile error、bash なら
  command not found 等）で、アサーションが判別したことにならない。新しいコード側を変異させ
  （ガード対象の条件・分岐・定数を 1 つずつ壊す）、テストがそれを捕まえることを確認する

これは TDD とは別軸で、順序を指定するものではない。TDD は実装より先にテストを書く順序の
規律で、こちらは書いたテストがガードである証拠の規律。TDD で red を目撃していれば 1 つ目の
分岐はそれで足りるが、新シンボル導入では red がシンボル不在による失敗になるので、2 つ目の
分岐は TDD でも埋まらない。

**変異を撃つ前に、破壊的な到達先が塞がれていることを確かめる**: 変異させるコードパスが
実環境の状態に触れうる（ファイル削除・外部 API 呼び出し・プロセス停止・ネットワーク書き込み）
なら、変異したテストはその操作を本当に実行しうる。「対処コマンドを提示する」を「実行する」へ
変える変異がこの形で、規約どおりの手順がそのまま事故の引き金になる。撃つ前に、到達先が stub で
塞がれていることを対照で確かめる。stub を置いた事実では足りず、テスト対象の実行経路で
呼び出しが stub に捕まることを 1 本の subtest で示す（PATH 等の差し替えが対象の経路に効いて
いるとは限らないため）。stub は実コマンドへ forward しない。`exec /bin/rm "$@"` のような
素通しは呼び出しを記録しても塞いではおらず、stub ではない。これは §5 の対照原理と同根で、
判別力の確認が「ガード対象が無いと落ちる」を確かめるのに対し、こちらは「破壊的な到達先が
塞がれている」を確かめる。

**変異を当てても落ちないなら、テストより先に変異を疑う**: 落ちない原因は、テストに判別力が
無いことのほかに、変異そのものが効いていないこと（未適用・no-op・到達不能・二重ガード）が
ある。後者をテストの欠陥と誤診すると、健全なテストを壊しに行く。fixture やアサーションを
触る前に、変異側を次の順で確かめる。

- `diff` 等で変異が実際に適用されたことを観測する。sed の pattern 不一致はエラーにならず
  黙って何もしないので、適用の成否は見ないと分からない
- 適用済みで落ちないなら、その変異が単体で挙動を変えるかを確かめる（別の入力を通す・
  該当コードを直接呼ぶ等で観測差が出るか）。変えないなら「その分岐は単体では挙動に
  効かない」というコードについての所見（no-op・到達不能）であり、テストの欠陥とは
  別物。変えるなら、そこで初めてテストの判別力を疑う
- 2 箇所を同時に壊して初めて差が出るなら二重ガードである。「1 つずつ壊す」変異では原理的に
  差が出ないので、組み合わせて壊す

さらに「ガード対象が無いと落ちる」だけでは足りず、**壊れうる入力形が fixture に入っているか**
まで見る。実装を無効化して落ちることは fixture が正常形しか持たなくても成立するので、
判別力チェックだけでは入力側の穴が残るため。対象は全テストではなく、既存データの末尾形状・
空・有無に依存して黙って壊れる処理（ファイルへの追記、文字列連結、parse）に絞る — 追記なら
「末尾改行あり / なし / 空ファイル / 既存 entry なし」が最小の組になる。

**「合成データを commit するな」型の指示との両立**: 検証に使ったスクラッチ artifact（一時
データファイル・使い捨てスクリプト）を commit しないことと、回帰テストを書かないことは
別物で、両立する。fixture をテスト内で生成すれば、データファイルもスクリプトも repo には
残らない。指示が回帰テストそのものを禁じていると読めるときに限り、確認して止まる。

**例外**: 再現条件をテストに落とせない場合（外部環境・実 API・タイミング依存など）は、なぜ
落とせないかを PR 本文に書いて明示する。テストに落とせるのにテストを書かなかったケースを、
例外に紛れ込ませて黙って通さないため。

由来: dotrc#37 / dotrc#76 / dotrc#82 / dotrc#84 / dotrc#93

### 5. 確認が空振りしていないか確かめる — 対照を取り、不在を待つ前に対象の存在を確かめる

「X を入れたら Y になった」を主張する測定は、X が無い状態も測る。X 無しでも Y になっていた
のなら、その測定は X の効果を何も示していない。Y を成立させうる他の要因が同時に存在して
いないか（交絡していないか）まで見て、切り分けが読み取れない測定は結論の根拠にしない。

これは §4 の「判別力を確認する」と同じ形である。あちらが「テストはガード対象が無い状態で
落ちなければガードではない」と言うのに対し、こちらは「測定は介入が無いと別の結果にならな
ければ証拠ではない」と言う。どちらも冒頭の『裏が取れるまで推測で先へ進めない』の一形態で、
裏取りの実体は介入の有無で結果が変わるという差分のほうにあり、測定を実行したという事実の
ほうには無い。

**書く側 — 他者へ渡す測定には対照を含める**。渡した先はその測定を土台に実装するので、交絡
したまま渡すと誤りが自分の手を離れてから展開し、訂正が派生物すべてに及ぶ。

**読む側 — 再実行しないのは費用の判断であって、健全性の判断ではない**。渡された実測を
再計測する必要は無いが、対照が手順に含まれているかを読むのは無料である。「裏取り済みなので
再計測は不要」と添えられていても、介入が無い状態を測っていない手順なら、その結論は保留する。

**不在を成功条件にする確認は、この空振りが常に付きまとう特殊ケース**である。「〜が無いこと」
「消えたこと」「失敗しなかったこと」を成功条件にすると、対象がまだ出現していない時点でも
真になる。`until ! <対象が居る>; do sleep 2; done` のような待機ループや、「エラーが出ない
こと」を pass 条件にするテストがこの形に当たる。ここでの対照は「対象が居るうちは偽になる」
ことなので、不在を待つ前に**存在・出現を確認してから待機に入る**。存在を確認できないなら、
その待機は結論の根拠にしない。既に対象の存在が別経路で分かっている（待機を仕掛ける前から
一覧に載っているのを見た等）なら、この手当ては要らない。

**特に踏みやすいのは、非同期に登録されるリソース**（background session、CI run、デプロイ、
キュー投入など）。起動コマンドが return した時点ではまだ一覧に載っていないことがあり、登録
前に不在チェックを始めると初回で真を引く。起動の完了と登録の完了は別物なので、コマンドが
return したことを登録の証拠として扱わない。

観測結果を doc や設計の前提として記録するときは特に効かせる。誤った観測は、それ自体の訂正
だけでは済まず、そこから派生した記述すべての撤回になるため。

由来: dotrc#59 / dotrc#76
