## rules / CLAUDE.md / skill の書き方

`.claude/rules/*.md` や CLAUDE.md に規約を書くときの指針。なぜこの形にするかという理由ごと
書くことで、agent が状況に応じて自分で判断できるようにする。SKILL.md / agent 定義も規約の
複写先になりうるので対象に含める（「規約の正典は rule に置き、skill / agent 定義からは
参照する」節）。frontmatter の `paths` のように rule ファイル固有の仕組みを扱う節は、
SKILL.md / agent 定義には当てはまらない。

由来: dotrc#8

### 理由を併記する

規約には「なぜそうするか／何を防ぐか」を本文に書く。理由は規約本体と同じくらい重要で、
agent が「この理由は今の状況に当てはまるか」を判断する材料になる。理由の無い裸の禁止は、
当てはまらない状況でも盲目的に避けられ、かえって作業を妨げる。

### 縛りは理由付きのソフト指針にする

断定的なハード禁止（「絶対〜禁止」「必ず〜する」）は避け、「（一般に／特定状況で）〜しない」
という形にする。明記した理由が当てはまらない特定状況では、agent がその手段を選べる余地を
残すため。例: main への直 push は一般に避けるべきだが、その理由（並行作業の巻き込み等）が
無い状況では選択肢になりうる。「禁止だから使わない」で思考停止させない。

縛り切りたい（判断の余地を残したくない）必須事項は、rules ではなく lint / test / hook へ
昇格する。rules は順守が不完全な指針であり、確実に止めたいなら機械的な強制（hook 等）の
ほうが適しているため。

### 領域固有なら paths でスコープする

特定領域でしか効かない規約は frontmatter の `paths`（グロブ配列）でスコープし、その領域の
ファイルを触ったときだけロードされるようにする。常時ロードはコンテキストを圧迫するため、
文脈依存の規約は paths でスコープするほうがよい。常時必要な規約だけ `paths` 無しにする。

### 規約の正典は rule に置き、skill / agent 定義からは参照する

複数の skill・agent・rule に共有される規約は、条文を rule に 1 つだけ置く。SKILL.md や
agent 定義はその条文を再掲せず、「詳細は `<rule>` の §N」のような参照に留める。

同じ条文が複数箇所にあると、規約を変えるときに片方だけ書き換わって矛盾し、次に読んだ agent が
どちらを根拠にするかで挙動が割れる。「両方直す」で防ぐのは書き手の注意力頼みで、規約が
増えるほど破れやすい。grep で残存箇所を探す検出も同じく書き換えのたびの注意に依存するので、
そもそも複写しない側で防ぐ。複写は、書き手がその場で読みやすい場所へ条文を置きたくなって
生まれることが多い。

skill / agent 定義に置いてよいのは、その skill 固有の手順・判断である。他所と共有される
規約が skill にしか書かれていないと気づいたら、rule へ引き上げてから skill 側を参照に落とす。

既存の複写を見つけたら、正典を 1 つ決めて残りを参照へ落とし、どれを正典にしたかを PR 本文に
書く。

由来: dotrc#125

### 由来は機構と記録に割り、記録はポインタだけ置く

由来の主な読者は「この規約はもう不要か」を判断する人間であって、規約を適用する agent では
ない。だが rule ファイルへ書けばロードのたびにトークンへ乗る。判定軸は**その文章が規約の
適用の助けになるか**で、由来を 2 つに割る。

- **再利用できる失敗の型になっているもの** — 実質は理由なので本文に残す。「由来」の
  ラベルは付けず、次に踏みかけたときの見分け方（何がどう黙って壊れるか）として書く。実例は
  残してよいが、固有名詞（PR 番号・日付・バージョン・repo 名・incident の経緯）は落として
  一般形にする。例: 「非同期に登録されるリソースは、起動コマンドが return した時点ではまだ
  一覧に載っていないので、不在チェックが初回で真を引く」
- **純粋な記録** — 本文には書かず、`由来: dotrc#59` の 1 行ポインタだけ置く。指す先はその
  規約を入れた PR で、物語はその本文にある。写せば二重管理になり、更新されない側が残る。
  番号が特定できない由来はポインタも付けずに落とす
  - `git log -S'<規約の一文>' -- <file>` で代用しない。`-S` が返すのは文言を入れた commit
    であって PR ではなく（`git log --merges --ancestry-path --reverse --oneline
    <sha>..origin/main | head -1` で絞る必要がある）、規約の一文が後で言い換えられれば空振りもする
  - 複数 PR を並べるときは各番号に `dotrc#` を付ける（`dotrc#37 / dotrc#76`）。rules は
    `~/.claude/rules/` へ展開されて**他 repo の session にもロードされる**ので、裸の `#78`
    では読んだ session がいる repo の PR に読めてしまう。自動リンクが目的ではない
    （GitHub の autolink は repo 内のファイルでは働かないので、`#78` に縮めてもリンクには
    ならない）

迷ったら記録側へ倒す。機構として書けるものは「由来」ではなく理由であり、それは「理由を
併記する」の節が既に本文へ要求している。裸の記録を本文へ置いても、適用時の判断は何も
変わらない。

**ポインタは節に隣接させる。** 節の末尾に置き、ファイル全体に掛かるものはタイトル直下の
導入段落の直後に置く。ファイル末尾へ集めて「観点 1 の〜の由来」のように散文で節を指すと、
節の改名・再構成で黙って空振りする。HTML コメントで書くのも同じ扱いで、コメントも
ファイルの一部としてロードされトークンに乗るので、記録を隠す置き場所にはならない。

**別の台帳ファイルを新設しない。** 保存先としては PR が既にあり、新設すると二重管理になって
更新されなくなる。

### skill の frontmatter に `effort:` を無自覚に置かない

長い自律 turn の途中で呼ばれる skill の frontmatter には、一般に `effort:` を置かない。
置くなら、下の 2 つの影響を見積もってからにする（`max` 等、上げる方向でも同じ 2 つの影響が
出るので、上げるときも同様に見積もる）。

**効く範囲が skill の外へ出る。** effort の上書きは skill の実行中で終わらない。Claude Code
公式 docs は `model` フィールドについて「上書きはその turn の残りに効き、次の prompt で
session の model に戻る」と明記している（`effort` フィールド自体の docs にはこの持続期間の
記述が無いが、実測では `effort` も同じ挙動を示した）。自律 turn では「次の prompt」がなかなか
来ないので、skill の後に続く作業がまとめて上書き後の effort で走る。機械的な作業向けの skill に
`effort: low` が付いていた委譲 session の実測では、その skill の後の PR 作成・自動レビューの
待機・レビュー判定役の起動・自己内省・完了報告まで low effort で走っており、低 effort の区間は
8〜24 リクエスト、最長 78 リクエストに達した。skill 名からは「その skill だけ安く回す」としか
読めないので、書き手も読み手も気づかない。

**多くのモデルでは切り替えが prompt cache を壊す。** effort が切り替わるリクエストは、その
時点までの文脈を cache から外して書き直す。実測では 100〜200k token の文脈が対象になった。
cache write の単価は cache read の 12.5〜20 倍（5 分 TTL は write が base の 1.25 倍で read 比
12.5 倍、1 時間 TTL は write が base の 2 倍で read 比 20 倍）で、切り替え 1 回で同じ文脈を
読む場合の 12.5〜20 倍を払う。1 時間 TTL が付くのは Claude subscription の主 conversation に
限られ、API key・cloud provider 経由や subagent の request は既定 5 分 TTL になる。skill を
1 回呼ぶと、入るときと戻るときの 2 回切り替わる。Fable 5.1 を API key か Claude subscription で
使う場合は既定でこの cache 破棄自体が起きない（v2.1.260 以降。Amazon Bedrock・Google Cloud の
Agent Platform・Claude apps gateway 経由や `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` 設定時、
組織が HIPAA 設定を持つ場合は対象外）。

見分けるには、effort 以外を同一にした skill と比べる。`effort:` が付いている側だけ、skill
呼び出し直後のリクエストで cache read が prefix まで落ち（実測 96k → 18〜24k）、cache write が
文脈の約 8 割へ跳ねる（実測 72〜78k）。付いていない側は cache read を保ち、write は数百 token に
収まる。既存 session の transcript で確かめるときは、隣接リクエスト間で `perTurnEffort`
（無ければ `effort`）が変わっていないか、`cache_creation_input_tokens` が大きいのに
`cache_read_input_tokens` が prefix 相当まで落ちたリクエストが無いかを見る。cache TTL を超える
待機でも後者は起きるので、effort の切り替えを伴うかで切り分ける。

理由が当てはまらない場合もある。

- skill の実行で session が実質的に終わる（後続作業が無い）なら、はみ出す先が無いので
  1 つ目の影響は小さい
- 機械的な作業を低 effort で安く回したいなら、その作業を低 effort の subagent へ切り出せば
  親の cache を壊さない。ただし文脈の再構築コストが乗るので、数リクエストで終わる作業では
  割に合わない
